## Summary

- **The business arithmetic is settled.** PRD v3 specifies an account margin in whole percentage points from 0% through 100%, defaulting to 10%; reservation grams are rounded up. Best-fit chooses the eligible spool with the least available stock after reservation, breaking ties by earlier creation and then ascending identifier. These are established inputs to planning, superseding older open questions. [PRD:119](../../foundation/prd.md#L119), [PRD:121](../../foundation/prd.md#L121)
- **The inspected reservation seam is unimplemented.** The spool and print migrations define independent records, the generated public function types are empty, print DTOs lack reservation state, and the spool mapper returns zero reserved grams. S-03 therefore introduces persistence and behavior, rather than enabling an existing hidden workflow. [Spool schema:14](../../../supabase/migrations/20261010000000_create_spools.sql#L14), [print schema:14](../../../supabase/migrations/20261012000000_create_prints.sql#L14), [types:82](../../../src/types/database.ts#L82), [print DTO:16](../../../src/lib/prints.ts#L16), [spool mapper:29](../../../src/lib/spools.ts#L29)
- **Safety includes existing writes.** Authenticated owners currently have direct update/delete privileges on their spools and prints. New endpoint checks would leave these paths outside the reservation invariant unless the database enforces it or privileges are deliberately changed. S-03 already owns rejecting stock corrections below reservations and cancelling reservations on spool/print deletion. [Spool grants:80](../../../supabase/migrations/20261010000000_create_spools.sql#L80), [print grants:106](../../../supabase/migrations/20261012000000_create_prints.sql#L106), [slice boundary:110](../../foundation/roadmap.md#L110)
- **Reuse the current collections and recovery patterns.** Stock already displays the intended gram fields; print refresh/save parsers must learn reservation state. A Chromium browser suite exists, and the migration preservation runner must be extended when the migration inventory changes. ### 1. Product contract and slice boundaries

The terms **spool**, **planned print**, **material**, **colour**, **recorded stock**, **reservation**, **available grams** and **account safety margin** come from the PRD requirements and business logic. Matching terminology also has an accepted contract in the archived stock and print plans. No domain glossary was found in the inspected context inventory; this investigation does not introduce aggregate names. [PRD:82](../../foundation/prd.md#L82), [PRD:115](../../foundation/prd.md#L115), [stock contract:19](../../archive/2026-10-10-personal-filament-stock/plan.md#L19), [print contract:21](../../archive/2026-10-12-personal-planned-prints/plan.md#L21)

For the US-01 inputs of a matching 150 g spool, two separate prints requiring 80 g each, and the default 10% margin, the first reservation is 88 g and leaves 62 g available. The second print cannot reserve from that spool until the first reservation is cancelled. Cancellation releases 88 g without reducing recorded stock. These quantities describe this named acceptance scenario, not arbitrary spool capacity. [PRD:48](../../foundation/prd.md#L48), [acceptance criteria:54](../../foundation/prd.md#L54), [cancellation semantics:123](../../foundation/prd.md#L123)

The calculation is `ceil(requiredGrams * (100 + marginPercent) / 100)`. With the PRD's separate 81 g requirement and 5% margin, the result is 86 g. Best-fit and manual choice apply the same margin; manual choice must be eligible and occurs before confirmation. The collection's display order is not the best-fit tie order. [PRD:69](../../foundation/prd.md#L69), [selection:119](../../foundation/prd.md#L119), [arithmetic and ordering:121](../../foundation/prd.md#L121), [stock display order:52](../../../src/lib/spools.ts#L52)

S-03 covers best-fit/manual reservation, insufficient-material feedback, cancellation and the existing-mutation safety transition. Account margin configuration belongs to S-04; automatic recalculation after reserved-print editing belongs to S-05; complete reserved-spool maintenance and cancellation feedback belongs to S-06; actual consumption belongs to S-07. The MVP still requires identifying automatically cancelled reservations. Planning must make the S-03/S-06 feedback boundary explicit rather than treating later work as permission for unsafe deletion. [Roadmap:110](../../foundation/roadmap.md#L110), [S-03:138](../../foundation/roadmap.md#L138), [S-04:150](../../foundation/roadmap.md#L150), [S-05:162](../../foundation/roadmap.md#L162), [S-06:174](../../foundation/roadmap.md#L174), [S-07:186](../../foundation/roadmap.md#L186), [PRD:112](../../foundation/prd.md#L112)

### 2. Persistence, matching and numeric bounds

The inspected spool and print table definitions contain owner IDs, requirements/stock, normalized labels and timestamps; prints also contain an optional name and version. They do not define a reservation relation or account margin storage. Their existing foreign keys cascade account deletion, not reservation cancellation after deleting a spool or print. A future reservation model needs explicit ownership and deletion semantics. [Spools:14](../../../supabase/migrations/20261010000000_create_spools.sql#L14), [prints:14](../../../supabase/migrations/20261012000000_create_prints.sql#L14), [database types:5](../../../src/types/database.ts#L5)

Material is normalized to uppercase in the database; colour preserves its normalized display case and has a generated lowercase `colour_key`, using ICU root casing. The accepted matching contract ignores case and redundant whitespace, preserves multicolour order, and does not merge synonyms. **Planning inference:** eligibility should compare the persisted canonical material and colour key rather than create a separate JavaScript matching algorithm. The existing public DTOs omit colour keys; the database can perform matching without adding them to public responses. [Stock agreement:25](../../archive/2026-10-10-personal-filament-stock/plan.md#L25), [normalization:33](../../archive/2026-10-10-personal-filament-stock/plan.md#L33), [spool trigger:38](../../../supabase/migrations/20261010000000_create_spools.sql#L38), [print trigger:59](../../../supabase/migrations/20261012000000_create_prints.sql#L59), [print projection:14](../../../src/lib/prints.ts#L14)

Spool stock is stored as `numeric` constrained to whole grams from 0 through 2,147,483,647, with positive stock required on insert. Print requirements use `numeric` constrained to whole grams from 1 through 2,147,483,647. The increased reservation amount can exceed the stock representation bound even when the base requirement is valid. Planning must define an insufficient-material result without an intermediate integer overflow or silent reduction of the required margin. Exact arithmetic belongs in the authoritative calculation; the browser preview must agree with it. These are implications of the existing bounds and PRD formula, not observed reservation behavior. [Spool bounds:25](../../../supabase/migrations/20261010000000_create_spools.sql#L25), [positive insert:91](../../../supabase/migrations/20261010000000_create_spools.sql#L91), [print bounds:30](../../../supabase/migrations/20261012000000_create_prints.sql#L30), [formula:121](../../foundation/prd.md#L121)

For a future reservation model, preserve the committed reserved amount across later account-margin changes. S-05 also needs to distinguish a manually chosen spool, and S-07 needs deterministic reservation creation ordering. **Planning implications:** retain enough reservation identity, selection provenance and creation information to support these documented consumers. Whether cancellation removes an active row or retains history, and whether the applied margin is stored separately, are design choices rather than existing requirements for a history screen. [PRD:61](../../foundation/prd.md#L61), [PRD:121](../../foundation/prd.md#L121), [PRD:123](../../foundation/prd.md#L123)

### 3. Transaction boundary and direct-write exposure

The stack decision places reservation and settlement operations in PostgreSQL functions exposed through Supabase RPC, with consistent locking and idempotency. Current application helpers instead use independent table inserts, updates and deletes. Neither list helper provides the transaction boundary needed for availability validation and reservation creation. [Stack decision:24](../../foundation/tech-stack.md#L24), [spool helpers:85](../../../src/lib/spools.ts#L85), [print helpers:98](../../../src/lib/prints.ts#L98), [paged read caveat:93](../../../src/lib/prints.ts#L93)

Current spool grants permit authenticated updates of material, colour and recorded stock, plus deletion. Print grants permit updates of name, material, colour and required grams, plus deletion. The inspected triggers normalize fields and protect identity; the print trigger advances its version. They contain no reservation checks. **Inference:** adding protections solely to Astro handlers would not protect these existing owner-authenticated direct writes after reservations are introduced. [Spool grants:80](../../../supabase/migrations/20261010000000_create_spools.sql#L80), [spool trigger:59](../../../supabase/migrations/20261010000000_create_spools.sql#L59), [print grants:106](../../../supabase/migrations/20261012000000_create_prints.sql#L106), [print trigger:80](../../../supabase/migrations/20261012000000_create_prints.sql#L80)

Planning needs a database consistency protocol covering reserve, release, guarded stock corrections, spool/print deletion, and changes to matching attributes or print requirements. A check of available grams followed by a separate unprotected write is not a proof of no overbooking. It must also address repeated reservation requests for the same print, competing prints targeting a spool, and a preview invalidated before confirmation. These are consequences of the PRD invariant and current write surfaces. [Invariant:41](../../foundation/prd.md#L41), [competing-request scope:145](../../foundation/roadmap.md#L145), [stock update:116](../../../src/lib/spools.ts#L116), [print update:130](../../../src/lib/prints.ts#L130)

The configured local database major version is PostgreSQL 17. At Read Committed, reads use statement snapshots; wrapping a read/check/write sequence in a transaction alone does not establish the inventory invariant. Row locks can coordinate writes, and PostgreSQL recommends consistent lock ordering to limit deadlocks. **Planning implication:** choose the shared lock target/order, reread availability after obtaining it, and account for direct writes. This research does not select or prove a particular locking implementation. [Local version:36](../../../supabase/config.toml#L36), [PostgreSQL isolation](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED), [PostgreSQL row locks and deadlocks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)

Current Supabase documentation prefers invoker security. If narrowed table privileges require definer functions, their elevated privileges require explicit ownership checks, a restricted search path with qualified relations, and restricted execution grants. An authenticated execution grant does not itself restrict returned rows by owner. **Design constraint:** retain caller ownership enforcement inside any privileged reservation operation; do not assume existing table RLS makes a definer function safe. Context7 resolved `/supabase/supabase` and retrieved the official database-function guide. [Supabase function security](https://supabase.com/docs/guides/database/functions#security-definer-vs-invoker)

### 4. API and read-model integration

The existing HTTP surface has collection GET/create and item update/delete routes under `/api/prints` and `/api/spools`. Mutations use form transport. The inspected validators reject unexpected fields, repeated/file-valued editable inputs and invalid quantities; routes derive ownership from the verified request user. New reserve/preview/cancel route names and payloads are not established contracts. [Print collection:16](../../../src/pages/api/prints/index.ts#L16), [print update:24](../../../src/pages/api/prints/[id]/update.ts#L24), [print delete:28](../../../src/pages/api/prints/[id]/delete.ts#L28), [print validation:161](../../../src/lib/print-validation.ts#L161), [spool validation:121](../../../src/lib/spool-validation.ts#L121)

Preserve the request-scoped Supabase client, verified `getUser()` identity, cookie overlay and accumulated response headers. Endpoint authorization remains necessary because the page redirect guard targets dashboard paths. Public operation inputs should identify the requested print/choice rather than trust client-supplied owners, reserved totals or availability. [Middleware:9](../../../src/lib/auth-middleware.ts#L9), [identity lookup:30](../../../src/lib/auth-middleware.ts#L30), [dashboard guard:53](../../../src/lib/auth-middleware.ts#L53), [client cookies:10](../../../src/lib/supabase.ts#L10), [print route ownership:27](../../../src/pages/api/prints/[id]/update.ts#L27)

`SpoolDto` already exposes `recordedGrams`, `reservedGrams` and `availableGrams`, but its mapper currently emits zero reserved and recorded-equals-available values. Reservation-aware reads must replace this placeholder in the shared service used by SSR, GET and mutation receipts. `PrintDto` lacks reservation metadata, and the print form and collection parsers explicitly reconstruct its known fields: extending the server DTO alone would discard new fields on those paths. [Spool DTO:13](../../../src/lib/spools.ts#L13), [mapper:29](../../../src/lib/spools.ts#L29), [print DTO:16](../../../src/lib/prints.ts#L16), [form parser:29](../../../src/components/prints/PrintForm.tsx#L29), [collection parser:25](../../../src/components/prints/PrintList.tsx#L25), [SSR caller:20](../../../src/pages/dashboard/prints.astro#L20)

Print edits use ID, owner and `expectedVersion`, distinguishing a stale owned record from an inaccessible/missing record after a failed conditional update. Spool edits and the inspected delete helpers have no expected-version predicate. The database print trigger increments versions even for direct updates, but does not require a caller version predicate. Whether reserve/release should also invalidate an open print edit needs an explicit contract. [Print update:130](../../../src/lib/prints.ts#L130), [spool update:116](../../../src/lib/spools.ts#L116), [print delete:168](../../../src/lib/prints.ts#L168), [spool delete:139](../../../src/lib/spools.ts#L139), [version trigger:80](../../../supabase/migrations/20261012000000_create_prints.sql#L80)

The response modules already provide private cache headers, validation/authentication/missing-record errors, database failure mapping and print edit conflicts. New business outcomes such as insufficient stock or an invalidated selection need deliberate mappings: current generic database fallbacks do not establish them. Print mutation failures carry uncertainty/refresh guidance; stock responses lack that operation distinction. Extend the appropriate boundary without turning business failures into generic internal errors. ### 5. UI integration and uncertain outcomes

`PrintList` owns collection state, pending/refetch coordination and a collection uncertainty guard. Its current row renders base requirements and Edit/Delete actions. Stock separately owns its collection and already binds the recorded/reserved/available values. The dashboard pages instantiate these collections independently; the inspected components do not share a reservation cache or subscription. **Inference:** reconcile the affected print state and stock quantities using authoritative reads or committed receipts; an already-open other page remains stale until it rereads. [Print state:65](../../../src/components/prints/PrintList.tsx#L65), [print row:440](../../../src/components/prints/PrintList.tsx#L440), [stock bindings:250](../../../src/components/spools/SpoolInventory.tsx#L250), [print page:52](../../../src/pages/dashboard/prints.astro#L52), [stock page:53](../../../src/pages/dashboard/spools.astro#L53)

The existing print pattern treats network failures, unreadable success receipts and server-error mutation replies as potentially committed operations. It blocks repeat mutations until a readable fresh list replaces local state; failed refresh preserves the draft/guard. S-03 can reuse this recovery behavior for reservation and cancellation. The server still needs replay/concurrency semantics: a disabled button cannot protect separate tabs or requests. A stale cancellation should identify its intended reservation so it cannot accidentally release a later replacement; that is a planning risk, not an observed current bug. [Form submission:125](../../../src/components/prints/PrintForm.tsx#L125), [uncertainty handling:168](../../../src/components/prints/PrintForm.tsx#L168), [collection guard:158](../../../src/components/prints/PrintList.tsx#L158), [refresh:207](../../../src/components/prints/PrintList.tsx#L207)

Existing inline panels, feedback styles, Button and FormField provide the design/accessibility seams. No reservation selector is present in the inspected shared UI files. Keep handlers and collection state in the owning collection as required by the repository guidelines. Update the page's “future safety margin” copy while retaining the distinction between entering a requirement and reserving stock. [PRD selection:119](../../foundation/prd.md#L119), [inline panel:489](../../../src/styles/global.css#L489), [feedback:508](../../../src/styles/global.css#L508), [Button:7](../../../src/components/ui/button.tsx#L7), [FormField:29](../../../src/components/ui/FormField.tsx#L29), [page copy:38](../../../src/pages/dashboard/prints.astro#L38), [form hint:316](../../../src/components/prints/PrintForm.tsx#L316), [repository UI rules](../../../AGENTS.md)

## Architecture Insights

The current path is SSR page → owner-scoped service → request Supabase client, with React forms using the same service through form-encoded endpoints. Preserve canonical committed values and affected-row confirmation when introducing RPC. Matching, availability checks and reservation writes require a shared authoritative database boundary; presentation reads and a browser preview do not provide that boundary. This follows from the observed services and the selected stack.
