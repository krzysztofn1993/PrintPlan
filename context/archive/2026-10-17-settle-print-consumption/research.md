# Research: S-07 — Settle actual print consumption once

**Date:** 2026-10-17T09:52:20+02:00

## Research Question

For roadmap S-07, what requirements, existing contracts, implementation seams, concurrency risks and unresolved choices must inform an implementation plan for actual-consumption settlement?

The supplied `s-07` resolves to change ID `settle-print-consumption`. No corresponding active or archived change folder existed at discovery, so this investigation creates the active identity and research artifacts. The roadmap names S-03 as the prerequisite and lists S-04/S-05/S-06 as parallel work. This research does not approve a plan or implement the feature. [Roadmap:184](../../foundation/roadmap.md#L184)

## Summary

- **The settlement policy is settled; its persistence and application flow are missing in the inspected implementation.** Deduct actual consumption, release the completed print's reservation, and cancel other reservations on that spool newest first until they fit. Consumption above recorded stock is allowed: record zero estimated stock, cancel the other reservations, and explain that the entered estimate was exceeded. A print cannot be settled twice. The inspected migrations, print read model and reservation RPCs do not represent that terminal state. [PRD:31](../../foundation/prd.md#L31), [PRD:121](../../foundation/prd.md#L121), [PRD:125](../../foundation/prd.md#L125), [Print schema:14](../../../supabase/migrations/20261012000000_create_prints.sql#L14), [Reservation schema:7](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L7), [Print DTO:25](../../../src/lib/prints.ts#L25)
- **Reuse the existing transactional boundary.** The supported stock, print and reservation mutations acquire an owner mutex before reading product state. Settlement must coordinate with that protocol, preserve request evidence and advance affected print versions. Idempotency by request key is insufficient by itself: a different key must not settle the same print again. [Lock:55](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L55), [Reserve:267](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L267), [Release:312](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L312), [Once-per-print requirement:42](../../foundation/prd.md#L42)
- **Recovery needs an operation result as well as current rows.** Existing refresh reads planned prints and clears uncertainty; its DTO has no settlement result, cancellation attribution or exceeded-estimate flag. Planning needs a durable, owner-scoped result/recovery contract that preserves the required feedback after an unreadable acknowledgement. This is an architectural implication of the inspected read path and product requirements, not an existing receipt implementation. [Refresh:220](../../../src/components/prints/PrintList.tsx#L220), [Decoder:8](../../../src/lib/print-dto.ts#L8), [Feedback requirements:112](../../foundation/prd.md#L112)
- **Extend existing verification rather than setting up another runner.** SQL, controlled concurrency, populated upgrades, HTTP smoke and Chromium recovery suites are present. Settlement remains an explicit test-strategy exclusion pending S-07. Existing test source and historical pass reports do not establish runtime settlement correctness. [Test strategy:183](../../foundation/test-plan.md#L183), [CI:51](../../../.github/workflows/ci.yml#L51), [CI:87](../../../.github/workflows/ci.yml#L87)

## Detailed Findings

### 1. Required behavior and slice boundaries

The PRD supplies the following rules for this flow:

- Actual consumption reduces **recorded stock**, rather than the reservation amount or the available balance. Releasing the completed print's reservation is part of settlement. Reservation creation and ordinary cancellation do not consume stock. [PRD:123](../../foundation/prd.md#L123), [PRD:125](../../foundation/prd.md#L125)
- If surviving reservations exceed the new recorded stock, cancel them in `created_at DESC, id DESC` order, stopping when the remaining total fits. Equal timestamps use descending reservation identifier; this ordering is a requirement, not a planning choice. [PRD:101](../../foundation/prd.md#L101), [PRD:121](../../foundation/prd.md#L121)
- If actual consumption exceeds the pre-settlement recorded stock, allow the settlement, set estimated stock to zero and cancel the other reservations on that spool. Explain that the estimate was exceeded without claiming that the physical spool is necessarily empty. Equality with recorded stock does not meet the documented “exceeds” condition. [PRD:113](../../foundation/prd.md#L113), [PRD:125](../../foundation/prd.md#L125)
- Identify automatically cancelled reservations, preserve user isolation and persisted data, and make the flow usable on phones and the specified desktop browsers. [PRD:110](../../foundation/prd.md#L110), [PRD:129](../../foundation/prd.md#L129)
- Repeated clicks and retries must not deduct consumption again for the same print. [PRD:42](../../foundation/prd.md#L42)

S-07 can proceed from implemented S-03 without introducing account-margin settings, automatic reserved-print recalculation or the full reserved-spool maintenance flow. Actual consumption is entered separately; the settlement rule does not instruct applying a safety margin to that value. The reservation's stored grams remain relevant to release, not the amount consumed. [Roadmap:184](../../foundation/roadmap.md#L184), [PRD:119](../../foundation/prd.md#L119), [PRD:125](../../foundation/prd.md#L125), [Reservation snapshots:12](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L12)

**Derived arithmetic for planning:** let `S` be recorded grams immediately before settlement, `A` the submitted actual grams under the eventual validation contract, and `O` the grams in other active reservations on that spool after releasing the completed print's reservation. The required new recorded amount is `max(0, S - A)`. If `O` exceeds that amount, cancel a newest-first prefix until surviving reserved grams are at most that amount; available grams then equal new recorded grams minus surviving reserved grams. Rejecting solely because `A` exceeds currently available grams would bypass the required automatic cancellation policy. This formula is derived from the PRD and the current inventory projection; it is not implemented settlement code. [PRD:125](../../foundation/prd.md#L125), [Inventory projection:81](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L81)

### 2. Storage, ownership and transactional integration

The inspected migration inventory defines stock, planned-print requirements and current reservations. `print_reservations` stores owner, print, spool, reserved grams, margin snapshot, selection provenance and creation time. Its unique print key prevents simultaneous active allocations for that print; composite owner foreign keys enforce matching ownership, and parent deletion cascades the allocation. These rows do not constitute a durable settlement record. [Inventory:11](../../../scripts/migration-persistence.mjs#L11), [Print schema:14](../../../supabase/migrations/20261012000000_create_prints.sql#L14), [Reservation schema:7](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L7)

The supported mutation set inspected here is create/update/delete spool, create/update/delete print, reserve and release. These RPCs use `auth.uid()`, explicit ownership checks, an empty search path and the shared owner mutex. The reservation migration revokes direct authenticated product-table mutation privileges and grants the supported functions. A settlement endpoint cannot rely on browser controls or route authentication alone; direct RPC execution must preserve those guarantees. The selected stack already calls for database functions for reservation and settlement. [CRUD RPCs:105](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L105), [Reserve:258](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L258), [Release:306](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L306), [Privileges:333](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L333), [Stack:24](../../foundation/tech-stack.md#L24)

The owner mutex is a private row locked with `FOR UPDATE`. Existing mutation functions acquire it in an earlier statement before state-dependent product reads. The accepted S-03 protocol is `VOLATILE` functions under Read Committed, with reads after the lock wait so they observe the preceding commit. **Planning implication:** put settlement's checks, stock deduction, own-reservation release, collateral cancellations, terminal evidence and receipt persistence inside the same transaction and serialization protocol. Do not replace that protocol with an independent settlement-specific lock. This is a compatibility requirement inferred from current mutators and the recorded design. [Lock helper:55](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L55), [Stock correction:124](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L124), [Reserve sequencing:267](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L267), [Accepted sequencing:61](../../archive/2026-10-16-reserve-and-release-material/plan.md#L61)

The current stock-correction RPC rejects stock below reserved grams. Settlement has a different documented transition: it may cancel reservations to restore the invariant. Calling the stock-correction flow before releasing/cancelling reservations would encounter its guard rather than implement settlement. Keep the committed invariant while designing the combined operation. [Correction guard:127](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L127), [PRD guardrail:41](../../foundation/prd.md#L41), [Settlement:125](../../foundation/prd.md#L125)

The print trigger increments version on updates, including `SET name = name`. Reserve, release and spool-deletion cancellation use that mechanism to invalidate stale clients. Settlement must account for the completed print and the surviving prints whose reservations it cancels; the actual representation and update statements belong in the plan. [Version trigger:80](../../../supabase/migrations/20261012000000_create_prints.sql#L80), [Deletion invalidation:157](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L157), [Reserve invalidation:301](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L301), [Release invalidation:321](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L321)

### 3. Replay, terminal identity and reservation evidence

`private.reservation_requests` retains original successful command parameters and reservation identity, keyed by owner/request ID. Its state permits `active`, `released` and `deleted`; its print/spool identifiers have no parent foreign keys. Existing deletion functions therefore preserve replay evidence after removing product rows. The ledger is reservation evidence, not once-per-print settlement evidence. [Ledger:40](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L40), [Print deletion:202](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L202), [Spool deletion:143](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L143)

Reserve checks retained request evidence before current print/version checks. When retained state is `active`, reusing a successful request with identical parameters reports its active reservation; changing parameters conflicts; a terminal request produces `reservation_request_completed`. Settlement and its automatic cancellations must retire matching reserve-request evidence intentionally. Otherwise, replaying a former reserve command can still report `active` even though its allocation has been removed. Whether to reuse an existing terminal state or introduce a new state is a schema/API design choice. [Replay branches:268](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L268)

Release targets the owner, print and exact reservation identity retained in the ledger. A delayed release of a former reservation does not delete a replacement reservation. Preserve that property when handling settlement and collateral cancellations. Likewise, a delayed settlement request must not silently consume a replacement reservation's spool; the plan must define the expected reservation/version inputs and conflicts. [Release identity:313](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L313), [Replacement test:114](../../../supabase/tests/reservations.test.sql#L114), [Browser release:423](../../../src/components/prints/PrintList.tsx#L423)

**Planning implication:** enforce durable uniqueness/terminal state by print identity as well as any request-key replay semantics. Define the outcomes for the same key with different actual grams and a different key for an already settled print. Decide how evidence survives later print/spool deletion. A client-side pending flag, a removed reservation, or an expected-version check alone does not encode the PRD's durable once-per-print rule. [PRD:42](../../foundation/prd.md#L42), [Current mutable print state:180](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L180), [Current reserve eligibility:276](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L276)

### 4. Read models, API and collection behavior

`planned_prints` left-joins active reservations. `PrintDto` and its browser decoder represent requirements, version and nullable reservation, with no settled discriminator or actual-consumption result. The decoder reconstructs the accepted fields, so adding a JSON property to an endpoint alone would discard it in the browser. If a settled print remains visible with a null reservation, the current list offers Reserve material, Edit and Delete. The plan must explicitly connect persistence, projection, database types, server mapping, decoder and action predicates. [View:93](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L93), [Read columns:22](../../../src/lib/prints.ts#L22), [DTO:25](../../../src/lib/prints.ts#L25), [Decoder:8](../../../src/lib/print-dto.ts#L8), [Actions:707](../../../src/components/prints/PrintList.tsx#L707), [Types:80](../../../src/types/database.ts#L80)

The existing reservation endpoint is a usable transport pattern: verified request identity, private JSON responses, form validation, service call and named business failures. Settlement needs its own payload/receipt and conflict contract; the current reservation mapper does not define settlement outcomes. [Reserve route:15](../../../src/pages/api/prints/[id]/reservation/reserve.ts#L15), [Response policy:5](../../../src/lib/reservation-response.ts#L5), [Failure mapping:27](../../../src/lib/reservation-response.ts#L27)

Reserve and release services perform projection reads after the mutation RPC. Those reads can fail after commit. The current UI treats transport failure, server failure or malformed success as uncertainty and blocks mutation pending review. A fresh UUID is generated inside each reservation confirmation; the UI does not retain it for exact replay. Settlement therefore needs explicit server guarantees for new-key retries and an intentional recovery path, rather than assuming the current browser token behavior supplies them. [Post-commit read:158](../../../src/lib/reservations.ts#L158), [Release read:224](../../../src/lib/reservations.ts#L224), [Request generation:351](../../../src/components/prints/PrintList.tsx#L351), [Uncertainty UI:595](../../../src/components/prints/PrintList.tsx#L595)

`refreshList` reloads `/api/prints`, clears uncertainty and closes inline panels. It does not refresh the separately owned spool inventory or retrieve an operation receipt. Current reservation success updates the local print row, rather than storing the returned stock DTO. **Planning implications:** reconcile affected print rows and provide a current recorded/reserved/available stock review surface; preserve identifiable automatic-cancellation details and the exceeded-estimate warning across lost acknowledgement. Current rows alone cannot attribute which cancellations belonged to that settlement, because the inspected projection contains neither operation identity nor cancellation history. [Refresh:220](../../../src/components/prints/PrintList.tsx#L220), [Success handling:376](../../../src/components/prints/PrintList.tsx#L376), [Separate inventory:157](../../../src/components/spools/SpoolInventory.tsx#L157), [Projection:93](../../../supabase/migrations/20261016000000_reserve_and_release_material.sql#L93), [Required feedback:112](../../foundation/prd.md#L112)

Existing routes return an expired-session response with a sign-in URL, but the inspected reserve/release UI handlers use generic fallback messages for that response. A settlement form should specify its session-expiry recovery rather than assume it inherits the form/list UX. Keep state and API mutations in the owning print collection, with presentation using the shared shell, form fields, buttons and Carbon feedback styles. [Session response:24](../../../src/pages/api/prints/[id]/reservation/reserve.ts#L24), [Release fallback:465](../../../src/components/prints/PrintList.tsx#L465), [Shared field:18](../../../src/components/ui/FormField.tsx#L18), [Button:7](../../../src/components/ui/button.tsx#L7), [Dashboard rules](../../../AGENTS.md)
